## From an embedded translator to a district platform.

We initially explored translation inside existing school software. As the work developed, we needed space to coordinate document intake, review, approval, and family access. That shifted the direction toward a standalone platform.

<Flow
  rows={[
    {
      steps: [
        { label: "Stage 1", text: "Embedded translation", note: "A translation feature inside existing school software." },
        { label: "Stage 2", text: "Standalone prototype", note: "A separate space for intake, review, approval, and family access.", state: "focus" },
        { label: "Stage 3", text: "V2 with Aeries", note: "School records and language information join the platform." },
      ],
    },
  ]}
/>

State law puts the translation duty on the district, and districts already have a person check important translations. The district became the buyer, and staff review became part of the product.

<p class="note">Cal. Educ. Code § 48985 · OUSD Board Policy 5124 · 34 CFR § 99.31</p>

## Completing the flow was only part of the test.

We tested whether people could follow the document journey and whether the review process fit an administrator’s workload. With 120 teachers sending forms, reviewing every document would not fit an administrator’s day. Two sessions changed the interface.

## What I learned

### Research can change the shape of the product.

Investigating the document gap expanded the work into a workflow connecting several people.

### A safeguard that nobody has time to use is still a delay.

Testing made the workload behind review visible and gave the next iteration a clearer focus.

### Building makes the next questions concrete.

Working in code lets me examine the handoffs and interactions that static screens leave open.
